## Dimensiones

| Dimensión | Riesgo si demand hunting mal diseñado | Mitigación conceptual |
|---|---|---|
| Carga cognitiva | Formulario complejo + nueva metáfora “solicitud” | Empezar simple; reutilizar lenguaje de búsqueda |
| Esfuerzo de búsqueda | Duplicar Google con pasos extra | Solo escalar a solicitar tras fallo corto |
| Incertidumbre | “¿Alguien me contestará?” | Match auto + ETA + cierre |
| Ansiedad de compra | Esperar y perder oferta | Notificar con frescura; no retrasar outbound |
| Fatiga de comparación | 12 hunters responden | Rank / dedupe / top-N |
| Confianza | Respuestas basura | Quality gates |
| Sensación de control | Caja negra IA | Mostrar por qué se sugirió |
| Expectativa de respuesta | SLA implícito de helpdesk | Copy honesto Modelo A vs B |
| Tolerancia a esperar | Urgencia mal clasificada | Detectar urgencia → path retailer/C |
| Percepción de fracaso | Silencio | Empty states honestos; alternativas |

## Pregunta clave

> ¿Una “búsqueda inteligente” reduce esfuerzo o agrega otra interfaz?

**Hipótesis (E1):** reduce esfuerzo **solo si**:

1. Reutiliza hábitos (buscar → resultados) sin forzar “crear solicitud” primero; y/o  
2. Tras 0 resultados útiles, un solo paso de “avísame / pide ayuda” es más barato que abrir 5 apps; y  
3. Los resultados son mejores que el siguiente mejor alternativa del usuario.

Si C introduce un lenguaje nuevo (“intent parser”, “mission”, “hunt ticket”) sin mejor outcome → **aumenta** carga.

## Implicación

El camino de menor arrepentimiento cognitivo: **mejorar BUSCAR + match catálogo** antes de enseñar un modelo mental de dos lados.
