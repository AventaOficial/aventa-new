# S6.4 — Deal Alerts Persistence + Real Candidate Index

## Purpose

Persist `AlertSubscription` as source of truth and retrieve candidates in DB — without delivery.

## Discovery

| Existing | Role vs S6.4 |
|----------|----------------|
| `auth.users` | Ownership root (`user_id`) |
| `profiles` (`id` = auth.users) | Profile only — **not** alert subscriptions |
| `profiles.preferred_categories` | Feed/onboarding — **not** AlertSubscription authority |
| `user_email_preferences` | Digests — **not** deal alert matching |
| `notifications` | In-app inbox — delivery BC (S6.5+) |

**Decision:** new table `deal_alert_subscriptions`. No parallel user table.

## Schema

See `supabase/migrations/20260919204823_deal_alert_subscriptions_s64.sql`.

### JSONB vs columns

| Field | Storage | Why |
|-------|---------|-----|
| `stores`, `categories` | `text[]` + **GIN** | Multi-value matching; indexable overlap/`@>` |
| `minimum_discount_percent` | `numeric` + btree (partial enabled) | Threshold prefilter |
| `enabled` | `boolean` | Scale path filter |
| `notification_channels` | `text[]` | Not a candidate dimension (passed through to S6.2) |
| Whole row as JSONB | **Rejected** | Would sacrifice queryability |

No normalized membership tables in S6.4: GIN on arrays is enough at current scale; revisit if update churn + cardinality explode.

## Multi-value

Empty `stores` / `categories` = wildcard on that dimension (`is_broad` / `fanout_class`).

## Soft-disable vs DELETE

**Prefer `enabled=false`** for auditability. Owner DELETE allowed via RLS (no audit table yet).

## Versioning / races

- Column `version` + optimistic concurrency on update (`expectedVersion`).
- Candidate evaluation uses **snapshot semantics**: one RPC result set ordered by `id`; mid-flight user edits do not mix inside a single fanout.

## Candidate index

```
Opportunity → deal_alert_find_candidates (SQL coarse)
            → CandidateSet (limit+1 overflow detect)
            → decideDealAlert (S6.2 fine)
            → fanoutDealAlert
```

`PostgresSubscriptionCandidateIndex` implements `SubscriptionCandidateIndex`.  
False positives from SQL are OK; S6.2 decides.

## Query / indexes

| Index | Query |
|-------|-------|
| `(enabled, minimum_discount_percent) WHERE enabled` | Threshold + enabled |
| GIN(`stores`) | Store/merchant membership |
| GIN(`categories`) | Category membership |
| `(user_id, enabled)` | User list / caps |
| `(fanout_class) WHERE enabled` | Broad/high_fanout orchestration |

## Scale

- Target: O(candidates) after index, not O(all subscriptions).
- `candidateLimit` (default 1000, hard max 5000); `candidateLimitReached` → fanout **SUPPRESS** (no silent partial).
- `high_fanout` / `broad` metadata for future batching — not ML.

## RLS

- authenticated: CRUD own rows only (`auth.uid() = user_id`)
- `deal_alert_find_candidates`: **service_role only**

## Non-goals

Delivery, cron, providers, money path, production DDL without approval.
